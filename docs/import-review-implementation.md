# Local import review implementation

The import review panel reads one conversation's explicit statement membership from `.auto-bean/import-sessions/<session-id>.json`, lifecycle state from `statements/import-status.yml`, and extracted facts plus inline decisions from each parsed statement. The session contains membership, statement groups and price runs. The panel and HTML export show saved group names and members.

Each group stores `group_id`, `name`, `origin` (`user` or `agent`), `source_files` and one `parsed_group` path. Groups partition session membership exactly. Import defaults to one statement per group, accepts explicit user groups, or infers related statements that benefit from shared context. It persists groups before dispatch and preserves them on resume. Each group uses separate Process and Categorize subagents. The YAML stores one lifecycle entry per group. The shared parsed JSON stores all source sections under `statements`, including source-specific facts and approvals. A group is done only after every source passes written validation. Shared transfers still require coordination across groups.

## Workflow and ownership

The [canonical process flow](../plugins/auto-bean/references/import-review.md#process-flow) shows discovery/resume, parallel processing and categorization, human-input loops, review before writing, post-write validation and recovery, and the price and memory follow-ups. It is bundled with the plugin; this document links to that single diagram.

Agents use ordinary scoped file edits. Process owns source facts and processing outcomes; Categorize owns inline transaction decisions; Import owns account decisions, session membership, groups and status YAML. Write edits canonical ledger files after explicit approval; Prices owns price runs and separately approved price directives. Memory edits governed JSON, while the main thread maintains workspace `MEMORY.md`. The [ownership table](../plugins/auto-bean/references/common.md#ownership) identifies generated fields that agents preserve.

Chat approval remains in the conversation. Optional `approval` fields are internal panel confirmations, not records an agent must construct. Validation reports are generated by the validation operation. No document revision counter, persistence API, transaction copy, patch journal or action queue is part of the agent workflow.

Import serializes edits to the same document and ledger. Workers on distinct statements may proceed independently. Before a scoped edit, the agent rereads current contents and preserves intervening user or panel updates. Every ledger transaction retains source/account/row identities; a shared transfer has one owner and both source identities. Interrupted writes resume from actual provenance, adding only missing entries and reporting conflicts rather than blindly replaying an import.

## One validation operation

The plugin launcher exposes `validate --workspace <path>`, with optional `--session <id>` and `--stage review|written`. Skills invoke it through the common `auto_bean` shell helper. No Python API is required.

For a session, `review` checks artifact structure, source/status linkage, resolved decisions, proposed postings and baseline ledger validity. It does not assert that transactions have been written. `written`, the default, checks actual source-row coverage, exact reviewed postings and source narration/payee, duplicate references, transfer ownership/provenance, supporting directives, available closing balances and price results. Generated reports identify their stage and the checked evidence. Offsetting errors cannot pass merely because a total matches.

Closing balances are compared through their stated date in the relevant commodity. Missing balances remain unavailable; row/posting checks still apply. Import advances YAML directly only after a current passed written result. Changed evidence or ledger contents require a fresh check. Validation does not grant approval, write financial entries or advance status.

Without a session, the same operation checks the canonical ledger, status and governed memory JSON. It does not open historical session/statement artifacts. Advisory memory is not an import-session completion gate. Fetch success and written price validation remain distinct; no required commodities produces an explicit zero-job result. Financial memory learning requires accepted decisions and verified results, without extra memory blocks in import artifacts.

## Panel and static export

The plugin runs a bundled stdio MCP process with no hosted endpoint or HTTP listener. It serves bundled UI assets through the host bridge; end users do not need Node. Explicit workspace/session binding prevents session mixing.

The panel shows YAML statuses, accounts, reported/query balances, postings, inline input needs, panel confirmations, validator results and price runs. Internal content checks detect intervening edits, including direct agent file changes. A correction is saved before requesting continuation in the same conversation; a failed continuation can be retried without resubmitting the edit. The panel never writes ledger entries.

Export HTML creates a self-contained read-only snapshot with all saved rows and review evidence. It excludes unsaved edits and raw attachments. Evaluation capture retains a snapshot per executed import step, or an explicit unavailable-review page if no valid review exists. Exported pages have no live approval controls.

## Guidance and examples

Skills own workflow steps. Common guidance owns runtime setup, shared ownership and validation; the import reference defines field meanings and edge cases; the ledger reference owns query/directive mechanics. Write owns standalone review, which Init and Prices also reference. Memory examples and price execution details remain beside their skills.

There is one [group parsed example](../plugins/auto-bean/references/parsed-statement-output.example.json) and one [session example](../plugins/auto-bean/references/import-session.example.json). They describe a synthetic resolved import with source facts, account mappings, split/refund postings, an answered category question, reciprocal transfer links, optional panel confirmations and generated written-stage validation. The [status example](../plugins/auto-bean/references/import-status.example.yml) uses the same source identity. Never copy example confirmations or validation results into a live import.

The fixture contains six source rows representing five economic transactions, with EUR 1050.75 checking and EUR 600 savings closing balances. The session illustrates requested versus actual quote dates and separate price review. Quote and execution metadata are synthetic fixture values, not observations from a market provider.

## Verification boundaries

Local schema/runtime/UI/package checks and ordinary evaluation-code tests cover the implementation; current results are reported with the change. Review evaluation checks parsed postings while canonical financial files remain unchanged; the next explicit user instruction permits direct writes. The verifier independently checks actual rows, balances and authorization against the prior review checkpoint. It must not require an agent-authored approval field. Historical scores in the [Harbor baseline](../evals/harbor/BASELINE.md) retain their original build scope.

No Harbor execution is part of this change. Run its controls or live tasks only after an explicit user request. Previous desktop acceptance does not establish acceptance of the revised workflow; installed-host correction, approval and continuation should be checked when an installation refresh is requested.
